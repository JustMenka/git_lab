## Ожидаемый ответ

При выполнении git pull --rebase Git получает удалённые изменения и переносит
локальные коммиты поверх обновлённой удалённой ветки.

В результате должна получиться линейная история R → L′ без отдельного
merge-коммита. SHA локального коммита изменяется, поскольку Git создаёт его
новую версию с другим родителем.

Если первоначальный коммит L не публиковался, результат можно отправить обычным
git push, без --force.

Мой результат совпал с ожидаемым: история стала линейной, локальный коммит
получил новый SHA, оба изменения сохранились.

## Моё объяснение

Я использовал два независимых клона репозитория. В клоне A создал локальный
коммит L (433d6bc), не отправляя его на GitHub. В клоне B создал коммит R
(7ea190b) и опубликовал его.

Затем в клоне A выполнил git pull --rebase origin feature/task-06. Git получил
удалённый коммит R и повторно применил изменения локального коммита L поверх
него.

В результате появился новый коммит L′ (dbd8c0d). SHA изменился, потому что
изменился родитель коммита: раньше им был c41397b, а после rebase стал 7ea190b.

В отличие от merge, rebase не создал коммит с двумя родителями. История осталась
линейной.

Проверка показала, что local.txt содержит локальное изменение L, а remote.txt —
удалённое изменение R. Рабочая директория чистая, локальная и удалённая ветки
синхронизированы.

Обычного git push было достаточно, поскольку исходный локальный коммит L ранее
не публиковался и переписывать удалённую историю не потребовалось.
