## Ожидаемый ответ

При выполнении git pull --no-rebase Git должен получить изменения из удалённого
репозитория и объединить их с локальными изменениями через merge.

Поскольку в клоне A создан локальный коммит L, а в клоне B опубликован коммит R,
история ветки расходится. В этом случае Git создаёт merge-коммит с двумя
родителями: L и R.

Оба исходных коммита должны сохраниться в истории без изменения SHA, а итоговое
состояние проекта должно содержать изменения из обоих клонов.

## Моё объяснение

Для выполнения задания я использовал два независимых клона репозитория: A
(~/git-practice) и B (~/git-task05-B).

В клоне A создал локальный коммит L (f527732), добавив файл local.txt. Этот
коммит не отправлял на GitHub.

Затем в клоне B создал коммит R (fd1e051), добавив файл remote.txt, и
опубликовал его с помощью git push.

После этого локальная и удалённая истории разошлись, поскольку оба коммита имели
общего предка 61a720e.

Вернувшись в клон A, я выполнил git pull --no-rebase origin feature/task-05. Git
загрузил удалённый коммит R и объединил его с локальным коммитом L, создав
merge-коммит 2737270.

Проверка git show --no-patch --format="%h %p %s" HEAD показала, что у
merge-коммита два родителя: f527732 и fd1e051.

После объединения оба файла сохранились: local.txt содержит Локальное изменение
L, а remote.txt — Удалённое изменение R.

В результате Git сохранил обе ветви истории и объединил их без конфликтов. После
публикации merge-коммита локальная и удалённая ветки синхронизированы, рабочая
директория и индекс чистые.

Ожидаемый ответ: merge-коммит имеет двух родителей L и R.
